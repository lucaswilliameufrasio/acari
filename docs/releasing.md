# Releasing

## Versioning Policy

- This project follows Semantic Versioning (`MAJOR.MINOR.PATCH`).
- Use tags in the format `vX.Y.Z`.
- Update `CHANGELOG.md` before creating a release tag.

## Changelog generation (git-cliff)

The changelog is auto-generated from git history using [git-cliff](https://git-cliff.org).
The prepare-release workflow builds git-cliff 2.14.2 from its verified archive,
after applying a checked, version-specific manifest change that removes the
optional profiler, with the checked-in lockfile and `--no-default-features`; its remaining
dependency warnings and limitations are documented in `docs/dependency-upgrade-audit.md`.

Commits must follow [Conventional Commits](https://www.conventionalcommits.org/) format:

```text
feat: add --exclude flag
fix: handle empty config path
ci: bump Rust toolchain
docs: add security glossary
```

Types: `feat`, `fix`, `ci`, `docs`, `style`, `refactor`, `test`, `chore`, `perf`.

## Prerequisites (cargo-dist)

Everything is already configured. [cargo-dist](https://github.com/axodotdev/cargo-dist) handles:

- Cross-platform builds (Linux x86_64/arm64, macOS Apple Silicon, Windows x86_64)
- Tarballs/zips with SHA256 checksums
- Install scripts (shell + powershell)
- Homebrew formula (if enabled)
- GitHub Release creation with auto-generated changelog

**No GitHub configuration needed.** The workflow uses automatic `GITHUB_TOKEN`.

## Release Steps

### Automatic (recommended)

The `Prepare Release` workflow handles steps 1-3 automatically.

**Setup (one-time):**

1. Go to **Settings → Actions → General → Workflow permissions**
   - Select **"Read and write permissions"**
   - Check **"Allow GitHub Actions to create and approve pull requests"**
   - Save

2. Go to **Settings → Environments → New environment**

1. Go to **Settings → Environments → New environment**
2. Name: `release`
3. Add **Required reviewers**: `lucaswilliameufrasio` (or whoever must approve)
4. Save

Without this environment, the workflow will not proceed without manual approval.

**Running:**

1. Go to **Actions → Prepare Release → Run workflow**.
2. Enter the version number (e.g., `0.2.0`).
3. The workflow pauses for approval (check your email/inbox).
4. After approval, it creates a PR with:
   - Updated `CHANGELOG.md` (generated by git-cliff)
   - Updated version in `Cargo.toml`
5. Review the PR and merge it.
6. After merge, create and push the tag:

```bash
git tag v0.2.0
git push origin v0.2.0
```

The `Release` workflow will build artifacts, generate installers, and publish the GitHub Release.

### Manual (alternative)

1. Ensure branch is green (fmt, clippy, test).

2. Generate the changelog from git history:

```bash
# Preview unreleased changes
git cliff --unreleased

# Regenerate the full CHANGELOG.md (auto-detect version)
git cliff -o CHANGELOG.md
```

   Review and commit the updated `CHANGELOG.md`.

3. Create and push a release tag:

```bash
git tag v0.2.0
git push origin v0.2.0
```

4. The `Release` workflow in GitHub Actions will:
   - `plan`: calculate which artifacts to build
   - `build-local-artifacts`: compile for each target, generate tarballs/zips + checksums
   - `build-global-artifacts`: generate installers (shell + powershell)
   - `host`: create GitHub Release, upload artifacts, generate changelog
   - `announce`: placeholder for notifications

### Generated artifacts

For each tag, cargo-dist generates:

| File | Description |
|------|-------------|
| `acari-{tag}-{target}.tar.gz` | Packaged binaries (Unix) |
| `acari-{tag}-{target}.zip` | Packaged binaries (Windows) |
| `acari-{tag}-{target}.tar.gz.sha256` | Checksum |
| `acari-installer.sh` | Shell install script |
| `acari-installer.ps1` | PowerShell install script |

### Install via cargo-dist

```bash
# Latest release (shell)
curl -fsSL https://github.com/lucaswilliameufrasio/acari/releases/latest/download/acari-installer.sh | sh

# Specific version
curl -fsSL https://github.com/lucaswilliameufrasio/acari/releases/download/v0.2.0/acari-installer.sh | sh
```

### Release tool dependencies

CI and release build `cargo-dist` and `cargo-about` from versioned crates.io
archives. `scripts/build-release-tool.py` verifies the archive SHA-256, replaces
its bundled lockfile with the corresponding checked-in `tools/locks/` file,
and builds with `cargo install --locked`. Rust 1.99.1 is pinned in the jobs.
This fixes the dependency graph, not the compiler or final binary byte-for-byte.

Before updating either tool, verify the new archive checksum against crates.io,
update its lockfile and the versions in the script and workflows, audit both
tool lockfiles with `cargo audit --file tools/locks/<lockfile>`, regenerate the
license inventory with that exact `cargo-about` build, and run the release-tool
matrix. Do not substitute the upstream prebuilt tool: its dependency graph may
differ from the one audited here.

## Customization

To change targets, installers or other settings:

```bash
cargo dist init
```

Or edit `dist-workspace.toml` directly.

## Post-release

- Move completed entries from `[Unreleased]` into a new version section in `CHANGELOG.md`.
- Keep checksum validation instructions in `README.md` up to date.
